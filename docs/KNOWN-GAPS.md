# VolleyLive 1.4.5 – known gaps and limits

These are documented, not bugs to retest. "API" = the MySQL server in `server/` (the planned launch
backend). "Firebase" = the Firestore-only backend (`firestore.rules`). "Demo" = the offline demo build.

## Firebase-only gaps (the API server and the demo enforce these; Firestore rules cannot)

| # | Gap | Why rules can't do it | Mitigation |
|---|-----|------------------------|------------|
| FB-1 | **Photo hash can be forged** (QA R12-03). The app sends the photo's SHA-256 with the upload; rules trust that value. | Storage/Firestore rules can't read file bytes. | API hashes the bytes on the server. On Firebase it would need a Cloud Function (not deployed: no cloud changes). |
| FB-2 | **"On court right now" is not checked for a credited player** (QA R12-02 / D133-5). Rules only check that the player is on the team that won the rally. | Needs the rotation replayed from every event plus set lineups – rules have no loops. | API and demo refuse a bench credit (`not_on_court`); the Firebase scorer UI only offers on-court chips. |
| FB-3 | **No `profile_incomplete` gate on match creation in the rules.** Since 1.3.8 (V137-2) the API (`createMatch`: 403 `profile_incomplete` unless the user row has first/last name, date of birth and pincode – this also catches legacy `profile_complete=1` rows) and the demo refuse to **create** a match for an incomplete profile. Joining/being added to a match is not gated on any backend. Firebase rules don't look up `users/{uid}/private/registration`. | Extra `get()` on every match write would exceed the expression budget (match create is at the 1000 limit). | The app routes incomplete profiles to the registration form before anything else. |
| FB-4 | **No India Post lookup on Firebase.** Since 1.3.8 (V137-5) rules refuse unallocated prefixes (e.g. 100001; same prefix table as the API/core) and a client-written district/state, and the Firebase app no longer stores a district. So a Firebase profile has pincode only, never a district/state (the API stores the looked-up district). | No network calls from rules. | The API server does the lookup server-side. |
| FB-5 | **Feedback rate limit.** API: 5 burst then 1 per 12 min per user; demo: 5 per hour. Rules validate shape (stars 1–5, text ≤ 1000, own uid, server time) and – since 1.3.8 (V137-5) – accepted T&C and no control / zero-width / bidi characters (newline and tab stay allowed, as on the API). They can't rate-limit. | Rules can't count writes over time. | Add Firebase App Check / a Cloud Function before using Firebase in production. |
| FB-6 | **Admin feedback list shows no user name** (only uid). | No joins in Firestore. | API joins `users.name`. |
| FB-7 | **Admin flag is a custom claim** (`admin: true`) set by an operator. The app never creates it. | – | API uses `ADMIN_UIDS`. |
| FB-9 | **Email uniqueness on Firebase is claim-based** (1.4.0, V139-3; tightened in 1.4.1, V140-5/6). A new or changed email is claimed as `emails/{address}` (`{uid}`, create-only; read only by its owner or as "no such claim") in the same batch as the registration doc, and rules require that claim; since 1.4.1 the **old claim must be released** in the same batch when the address changes or is removed (`oldClaimReleased`, V140-5). **1.4.3 (V142-5/6): the address is checked against an ALLOW list, not deny lists.** The 1.4.1/1.4.2 deny lists kept missing characters (RE2's `\p{Lu}` is older than the app's Unicode – Tester found 288 capitals passing – and format characters such as U+FFF9–FFFB, U+0600–0605, U+13430 were not listed). Now (`firestore.rules emailOk`, same set as `src/core/emailChars.ts`, generated by `scripts/gen-email-chars.js` from Unicode 16 and compared by rules-tests): before the `@` a–z, 0–9, the RFC 5322 signs `! # $ % & ' * + - / = ? ^ _ ` { | } ~` and dots; after it letters, digits, `-` and dots, TLD 2+; plus 1,427 vetted letters – lower-case Latin (Latin-1, Extended-A/B, Extended Additional), Greek and Cyrillic (`Ll` only, NFC-stable, already case-folded) and the letters, marks and digits of Devanagari, Bengali, Gurmukhi, Gujarati, Oriya, Tamil, Telugu, Kannada and Malayalam. No capital, and no format (Cf), control (Cc), private-use (Co), unassigned (Cn) or separator (Zs/Zl/Zp) character, nor any default-ignorable, can pass. The app, API and demo use the same allow list (`core/registration.ts checkEmail`), so **Firebase never refuses an address the app accepted**: the app shows `email_chars` under the field (EN: "This address has a character we can’t accept…", HI: "इस पते में ऐसा अक्षर है…"). Trade-off: addresses in other scripts (CJK, Arabic, Georgian, Cherokee…) or with symbols are refused on every backend; **since 1.4.4 (V143-6) a stored address of that kind (accepted before 1.4.3) is kept as it is: the account's own unchanged address always passes on save** (core `checkRegistrationUpdate`, API, demo, rules `d.email == oldEmail`), so a pincode or name save works; only a new or changed address gets the checks. A wider list (Ol Chiki, Meetei Mayek, Arabic for Urdu/Kashmiri, ZWNJ/ZWJ inside Indic words) is prepared but **inactive** in 1.4.4 – see `docs/qa/RELEASE-1.4.4.md`. Remaining gaps: (a) accounts saved by 1.3.7–1.3.9 kept their address without a claim, so two such accounts can still share one, and a newer account can claim an address an older unclaimed account holds; (b) rules can't NFC-normalise – the allow list only has NFC-stable characters, but combining marks are allowed (Indian scripts need them), so a modified client could claim the decomposed twin of an Indic address as a second address – e.g. `ऩ` U+0929 (NFC) and `न` U+0928 + `़` U+093C (NFD) are both in the list, and the rules compare code points (1.4.4, V143-10: the 1.4.3 example `e` + U+0301 was wrong – U+0301 is not in the list, so Latin twins are refused). The app, API and demo always fold to NFC, so they never create the NFD twin, and the API's unique index sees both as one address; (c) "this address is taken" is observable (as on the API's 409); (d) claims made under 1.4.0, before the release rule, stay until their owner releases them. | Rules have no string normalisation and no queries over other users' private docs; a regular expression may be at most 4,096 characters (so the class is written as the characters themselves). | The API (utf8mb4_bin unique index + NFC) and the demo enforce it fully. Rules tests: "1.4.3: tester findings V142-5/V142-6" (every Cf/Cc/Zs/Zl/Zp code point, Co/Cn samples, capitals sample, every allowed letter). |
| FB-10 | **Daily-item tombstones written by 1.4.1 keep their text** until scrubbed (1.4.2, V141-6). Since 1.4.2 a delete blanks `textEn`/`textHi` and removes `attribution`/`sourceUrl` in the same write, and the rules require that (`tombstoneOk`); a 1.4.1 tombstone that still has text may only be scrubbed (stays deleted, same `removedAt`). The 1.4.2 admin app scrubs one when "Delete" is pressed on it again; **1.4.3: the admin script `scripts/admin/scrub-daily-tombstones.js`** (dry run by default, `--apply` to scrub; the admin's own credentials; not run by the release) blanks all of them at once – textEn/textHi '' and attribution/sourceUrl null, nothing else. Turned-**off** (not deleted) items keep their text – the admin needs it to turn them back on (a copy). | Rules can't run a batch job. | API and demo blank the text on delete too. |
| FB-8 | **In-memory rate limits on the API** (not Firebase, listed for completeness, R12-04): correct for one instance; set `REDIS_URL` when running more than one. | – | `REDIS_URL` support exists. |

## Data migrations (1.3.8 – 1.4.2)

- **0012_captain_verdict_backfill** (V137-1): matches approved/voided by an admin under 1.3.6 after the
  opposing captain had confirmed got no `captain_verdict` from 0010. 0012 sets `confirmed` where the old
  fields show a captain verdict without a dispute reason, and `rejected` where a dispute reason exists.
  **Ambiguity:** 1.3.6 stored a captain *rejection without a reason* exactly like a confirmation
  (`verified_by` set, `dispute_reason` NULL), so such rows become `confirmed` – which is also how 1.3.6
  counted them. The app/rules apply the same reading to legacy Firebase docs (`verification.by` without
  `captain`). (The request said "0011"; that number was already taken by `0011_feedback_daily_items`.)
- **0013_users_email_unique** (V137-8): unique index on the normalised email
  (`NULLIF(LOWER(TRIM(email)),'')`). Existing duplicates are not deleted: the oldest account keeps the
  address, the others get `email = NULL` and are listed in `email_duplicates_0013` (user id, old email,
  kept user id) for support to follow up. A save that loses the race gets `409 email_taken`.
  **1.3.9 (V138-1, V138-2): fixed in place** – 0013 had never been deployed to a real server. It now pins
  `utf8mb4 / utf8mb4_0900_ai_ci` on its table, compares emails with `utf8mb4_bin` on
  `LOWER(TRIM(email))` (case-insensitive only: `josé@` ≠ `jose@`, `straße@` ≠ `strasse@`), and every step
  is guarded, so it completes from the half-applied state the 1.3.8 file left on a DB whose default
  collation was different, and re-running it changes nothing. The migration runner runs each file on one
  connection.
- **0014_email_index_repair** (1.4.0, V139-1; **fixed in place in 1.4.1**, V140-1/2/3/9): for a database
  that recorded the **1.3.8** 0013 as applied – no need to recreate it. 0014 shipped in the 1.4.0 build but was
  never deployed to a server, and a failing 0014 would stop the runner before any new 0015 could repair it, so
  it was corrected in place (header comment; the 1.4.0 body is kept as
  `server/tests/fixtures/0014_as_shipped_in_1.4.0.sql` and tested as an upgrade path). What it does now:
  - the binary index is built under a temporary name **while the 1.3.8 index is still there**, then swapped in
    one `ALTER TABLE` (drop old + rename new) – the table is never without a unique email index;
  - a database left without an index by the 1.4.0 body (interrupted, then someone saved one of the restored
    addresses) is cleaned first: the restored copy is cleared again and re-listed in `email_duplicates_0013`;
  - log rows in `email_restored_0014` that were never applied are dropped and worked out again on every run,
    so a rerun re-checks everything; running it twice gives the same result (tests stop it after every 3rd
    statement and after logging);
  - an address 1.3.8 cleared is given back only where safe: the account still has no email, and no account
    holds the same address up to case/spaces (byte comparison, like the index) **or** canonical equivalence
    (`utf8mb4_0900_as_cs`: an NFD spelling of `josé@` counts as the same – V140-3); of two cleared accounts that
    clash, only the oldest gets it; the UPDATE runs with the unique index already in place, so it can't make a
    duplicate;
  - **latin1** databases (V140-2): 1.3.8 created `email_duplicates_0013` in the database default charset;
    0014 reads it with `CONVERT(... USING utf8mb4)` and never gives back a logged address containing `?`
    from such a table (it may be mangled: `ｒajw@` was logged as `?ajw@`) – it stays listed for support. Tested
    on a `latin1` database (fresh migrate and 1.3.8 → 1.4.1 upgrade);
  - **V140-9 (by design):** the value given back is `LOWER(TRIM(old email))` – case and spaces are dropped as
    the app does on save; NFC follows on the account's next save (V139-2). A **case-only duplicate** (the
    reason 1.3.8 cleared it) stays cleared while another account holds that address; if that account has since
    removed or changed its address, the address is free and goes back to the oldest cleared account – the
    normal "first come" rule, not a second owner.
  Restored accounts are listed in `email_restored_0014` and removed from `email_duplicates_0013`. On a
  correct database (index already binary, nothing logged) it changes nothing – no table, row or index.
- **0014, 1.4.2 (V141-1) – fixed in place again** (still never deployed; the 1.4.1 body is kept as
  `server/tests/fixtures/0014_as_shipped_in_1.4.1.sql`). The 1.4.1 body marked nothing, so a run stopped between
  its restoring `UPDATE` and its final `DELETE`, with the user changing or removing the address before the rerun,
  could give a removed address back, keep a log row for an address the user no longer had, or drop the
  `email_duplicates_0013` row. Now `email_restored_0014.applied` (0 candidate – only inside the transaction,
  1 given back, 2 superseded) and steps 4–6 run in **one transaction** (`START TRANSACTION … COMMIT`; the runner
  rolls back on failure and a lost connection rolls back by itself): candidates, the restore (only where the
  account's email is **still empty** at that moment – checked in the same statement that writes it), marking
  exactly the rows written, dropping the skipped ones and removing the restored ones from
  `email_duplicates_0013` happen together or not at all. A log table left by a 1.4.0/1.4.1 run gets the column
  once: a row whose user holds the address = 1; a row whose user saved their profile after it (changed or
  removed the address) = 2, never given back and left listed; the rest = 0 (worked out again).
  **Residual:** for such a legacy log only, a user who removed a restored address **without** saving anything
  else afterwards can't be told apart – that is the "saved after" test (`users.updated_at > restored_at`), and
  every profile save sets `updated_at`. Tests: `server/tests/fixes142.test.ts` (interrupted after the restore;
  1.4.1 body interrupted + email changed/removed; stopped after every 4th statement).
  **1.4.3 (Tester info, conservative under-restore):** if the 1.4.1 body stopped **before** its restoring
  `UPDATE` ran (log rows written, nothing given back) and the user then saved their profile with the email still
  empty, the legacy conversion sees "saved after the log row" and marks the row 2 (superseded): the address is
  **not** restored even though the account's email is still empty. This errs on the side of never giving back an
  address the user may have meant to drop; the row stays in `email_duplicates_0013` and the address can be set
  again by the user (or an admin) if it is still free. Accepted as is (0014 was never deployed anywhere).
- **Migration checksums (1.4.2, V141-1, additive):** `schema_migrations.checksum` (sha256 of the file, CRLF
  normalised) is recorded on apply; a database from before 1.4.2 gets the column and its current checksums on the
  next run. On every run all applied files are checked **before** anything new is applied: a changed file stops
  the runner (`MigrationChecksumError`, naming the files) unless it is in `CHECKSUM_ALLOWLIST`
  (`server/src/db/migrate.ts`) with the recorded checksum – then it is a warning. The allowlist holds only
  **0014** with its 1.4.0 and 1.4.1 checksums (fixed in place, never deployed). Note: a database whose checksum
  was first recorded by 1.4.2 trusts whatever file it had then. Migrations stay append-only (docs/DEPLOY.md).
  **1.4.3 (V142-4):** a NULL record or a missing `checksum` column (once the record has started –
  `schema_migrations_meta.checksums_since`, additive) stops the runner instead of being re-recorded; the 0014
  allowlist applies only when the file on disk is exactly the accepted 1.4.2+ version (`current`) **and** the
  record is one of its earlier hashes or `unknown`; a pre-1.4.2 database records 0014 as `unknown` (the version
  that ran can't be told: both bodies leave the same indexes) with a warning, the other files trust-on-first-use
  with a warning. Details and recovery: docs/DEPLOY.md "Migration checksums".
- **0015_daily_items_tombstones** (1.4.1, V140-7, additive): adds `daily_items.removed_at` (set once when an
  item is turned off or deleted) and `daily_items.deleted` (an admin delete is now a tombstone, not a row
  delete). Guarded, re-runnable.

## Legacy captain answers (V138-3)

A 1.3.6 client stored a captain's answer without the `captain` verdict. That shape ("approved/voided +
`by`, no `captain`": no reason = confirmed, a reason = rejected) is trusted **only for answers stamped
before 1.3.7** – `LEGACY_VERDICT_BEFORE` in `src/core/antifraud.ts` (2026-10-11 10:00 UTC, the 1.3.7
build). A newer answer without a verdict reads as unanswered. The rules require the verdict on every new
captain answer (reject with or without a reason) and on an admin approval of an answered match
(`captain == verdictFromOld(old)`), so an outdated (≤ 1.3.7) admin app can't turn a reason-less rejection
into a counted match. If a server stayed on 1.3.6 after that date, set the constant to the day it moved to
1.3.7+ (the API's 0012 backfill already wrote those verdicts).

## Fact of the day (V138-7, reworked in 1.4.0 for V139-4 and in 1.4.1 for V140-7)

Since 1.4.0 (`src/core/dailyItems.ts` `pickDaily` / `dailySlot`) the rotation is a sequence of **cycles**
starting 2026-01-01 IST. 1.4.1 made cycle membership depend only on stored **server timestamps that never
change afterwards** – `createdAt` (when added) and `removedAt` (when turned off or deleted, set once):

- a cycle that starts on IST day *c* holds the items that were on at the start of day *c* and added before it
  (bundled items and pre-1.3.9 docs have no `createdAt` and are always in), newest first, then the undated
  ones, ties by id; it lasts as many days as it has members, one per day; the next cycle starts the day after;
- **adding** an item never changes today's fact: it joins (and leads) the next cycle;
- **turning off or deleting** an item never changes today's fact **unless it is today's fact**: the item keeps
  its slot in every cycle that had already started (so every other day stays as it was), and its own
  remaining slot in that cycle shows a substitute – the next active member (seen twice in that cycle). From
  the next cycle on it is gone. Deleted items are kept as tombstones (`deleted`, no text in the public list);
  admins no longer see them; the Firestore rules refuse a real delete;
- **turning an item back on** creates a copy (new id and `createdAt`) and leaves the old one as a deleted
  tombstone, so it joins the next cycle like any new item;
- **gaps are bounded**: an item shown on day *d* is shown again within (its cycle's length) + (the next cycle's
  length) − 1 days; a cycle is never longer than the number of items on when it starts. Property tests
  (`src/core/__tests__/fixes141.test.ts`, 900-day random add/remove/reactivate schedules) check: today's fact
  never changes except when today's own item is removed, gaps ≤ 2 × the most items ever on (worst seen:
  1.28 ×), and the result is identical with the phone clock ±60 s off;
- **clock skew**: no comparison with the phone's clock is used for membership (a phone 60 s behind used to
  treat a just-added fact as "future" and reshape the rotation). The phone's clock only decides which IST day
  it is – the card switches at the phone's midnight. In the demo, timestamps are phone time (no server).

**1.4.2:** the API's public list sends **every active item** first and fills the remaining room (5,000 rows in
total) with the **newest** tombstones (V141-2: before, the oldest 5,000 rows of either kind were sent, so old
tombstones pushed the newest facts out). Only tombstones removed long ago – no longer holding a slot in a running
cycle unless there are thousands of items – are left out. A deleted item keeps no text on any backend (V141-6;
Firebase: see FB-10). Firebase creates must carry `createdAt` = server time (V141-3; an absent `createdAt` used
to put a new item in the running cycle). The admin API's `active` must be a real boolean (`"false"` / `0` were
taken as on).

Known limit: an item turned off **before 1.4.1** has no `removedAt`, so it is in no cycle (as in 1.4.0);
turning such an item off again isn't possible – turn it on (a copy) and off.

## Review prompt: where and when (V141-9, 1.4.2)

What 1.4.1 did (checked in code and in the browser): the prompt hook (`state/useReviewPrompt.ts`) was mounted
**only on the match page** (`match/[id]/index.tsx`). On the scoring screen nothing could ask, so closing the result
sheet there never showed it; opening the summary page within 10 minutes of the finish did (that is what QA saw
for Ishaan). A flagged (< 10 min) match **never blocked** it – no rule looks at the duration. Both statements in
the 1.4.1 report were correct; the behaviour was just inconsistent between the two screens.

Since 1.4.2 the scoring screen asks too, **once the result sheet has been closed** (Close, Escape/back,
backdrop) and nothing else is open (the hook waits for `uiBusy()` to clear, then 1.5 s): same rules everywhere –
won or POTM, ≥ 3 finished matches, 60-day cooldown, within 10 minutes of the finish (or seen finishing / just
confirmed on the match page). After a prompt the cooldown is stored, so the match page doesn't ask again.
Screenshots `42-03-rating-prompt-scoring-screen-*.png`.

## Review prompt clock (V137-4)

The 60-day "ask for a review" cooldown uses server time on the API (response `Date` header) and, since
1.3.9, on Firebase (`users/{uid}/private/review`: `checkedAt` / `lastAskedAt` are `serverTimestamp()`s;
rules allow only `request.time` or the unchanged value, owner only). **The demo uses the phone clock**: it
has no server, so changing the phone's date can show the mock review sheet again (nothing is sent).

**Why no prompt after a win (V140-13, 1.4.1 finding):** the prompt shows at most once per **60 days per
user**, stored on the phone (API/demo: `volleylive.review.lastAsked.<uid>`; Firebase: on the server), and only
after at least 3 finished matches. A flagged result (under 10 minutes) does **not** block it. In QA's session
Aarav had already been asked during the V139-7 check, so the later 3–0 win was inside the cooldown – working as
designed. What was wrong: **"Reset demo data" kept that 60-day mark**, so a reset demo stayed silent. Since
1.4.1 the reset clears every `volleylive.review.lastAsked.*` key (`DemoBackend.reset`); verified in the browser
(EN and HI): reset → 3–0 win → POTM → the mock review sheet appears (`41-05-rating-prompt-*.png`).

## Licences (V137-7)

About > Open-source licenses lists the whole **JavaScript production dependency tree** (transitive,
generated offline from `node_modules` at build time, with the licence/notice text each package ships).
Since 1.3.9 (V138-5) every installed package that **ships native code** (an Expo module config, an
`android/build.gradle` or a podspec – e.g. `react-native-gesture-handler`, which is a peer dependency and
was missed before) is included with its own dependencies, even when it is only a peer.
Native libraries added by Gradle (AndroidX, Play services, etc.) are **not** in the list; their notices
would need the Gradle `oss-licenses` plugin or a manual list before store release. Some packages ship no
licence file – the viewer then shows the declared licence id only.

## 32-bit ARM (V137-9)

The APK has no `armeabi-v7a` build, so 32-bit-only phones can't install it. Left unchanged by product
decision (it would also grow the APK).

C130-1 (sock-puppet opposing captain) is **not implemented** by decision – it stays an open item for Akshit.

## Web-only: no offline app shell (F135-3)

The web build has no service worker. A tab that is **already open** keeps scoring offline (rallies are
kept in browser storage and synced later, and the lists show the local score – F135-2), but **opening or
reloading** the site while offline shows the browser's offline page. Android/iOS are not affected (the app
bundle is on the phone). Adding an offline shell (Workbox / `expo-router` static export + service worker)
was not cheap enough for 1.3.7/1.3.8; the web app is a companion, the phone app is the product.

## Substitutions (R136-20)

Substitutions can be made **at the start of a set** (before its first rally) from the scoring screen
("Substitution"): the bench player takes the court player's position in that set's lineup. Mid-set
substitutions would need a new event type replayed by every backend (rules, API, demo) and are not in
1.3.7; pressing Substitution mid-set explains this.

## A finished match is final (V141-8, 1.4.2)

Once the winning rally is in, the score can't change on any backend (core `finishedScoreProblem` + `statusMoveOk`,
demo, Firebase client, API `writeMatch`, `firestore.rules finishedFrozenOk`): no undo, no extra rally, no move
back to live – **also before the Player of the Match is confirmed** (until 1.4.1 undo was allowed until then, and
closing the result sheet with Escape left "Undo · Back to 24–0" active). Still allowed: crediting one of the last
3 rallies to a player ("Who scored?", same rallies, same score) and picking the POTM. The scoring screen's Undo is
disabled with "Match over: the score is final" (HI: "मैच खत्म: स्कोर अब अंतिम है"), and the result sheet has no
"Undo last" button. **Consequence:** a wrongly entered winning rally can no longer be taken back by the scorer –
an admin can void the match (review flow) and the players can replay/re-enter it.

## Emails (V139-2 / V139-3, 1.4.0)

All three backends NFC-normalise, trim and lower-case an email before validating, comparing and storing it
(`core/registration.ts checkEmail` / `emailKey`), so `jose\u0301@` and `josé@` are one address; accents and
widths still count (`josé@` ≠ `jose@`, `straße@` ≠ `strasse@`), case and spaces don't. One address per
account: API (0013/0014 unique index, `409 email_taken`), demo (checked on save), Firebase (claims, see FB-9).
An address an older client stored decomposed is normalised on that account's next save. Since 1.4.1 (V140-3)
saving a profile whose address is **unchanged** (same key) never answers `email_taken`, even if another account
holds the normalised spelling – the legacy value is kept as stored until the user changes it. Since 1.4.1
(V140-4) Greek final sigma and other special lower-case forms fold like the server (`ς`→`σ`, `ſ`→`s`, `µ`→`μ`,
`ϐ ϑ ϕ ϖ ϰ ϱ ϵ ẛ ι`), and an address that still has an upper/title-case letter after folding is refused. Since 1.4.2 (V141-5) every
invisible character is refused on all backends – all Default_Ignorable_Code_Points (Hangul fillers
U+3164/115F/1160/FFA0, U+034F, zero-width, bidi controls, variation selectors, tags) and the Braille blank U+2800 –
and U+0345 folds to ι.

## Demo-only behaviour

- APS / Field Post pincodes (9xxxxx) are refused in the demo (no lookup); the API looks them up.
- The demo stores data on the phone only; demo data does not carry over to the live app.
- "Rate VolleyLive" opens a mock sheet in the demo; real in-app review only works once the app is
  published on Google Play / the App Store.

## Firestore rules tests: run serially (1.4.1 harness)

`rules-tests` talks to the Firestore/Storage emulators (`/workspace/scripts/emulator.sh start`). The suite
must run **serially** (`npx jest --runInBand`) and **not at the same time as another heavy job** (Gradle,
the app's jest run): a cold emulator can take over 60 s for the first request. The per-test timeout is 30 s
and the setup (`beforeAll`) timeout 120 s.


## 1.4.3 – a finished match is final (QA V142-1/2/3/7)

Once the winning rally exists, the match no longer changes on any backend. **Writable afterwards:** a credit on
one of the **last 3 rallies** (same rallies, same sides, only `playerId` / `kind`), the **POTM**, and the admin /
captain fields (`verification`, `confirmedAt`) plus the server stamps. **Frozen** (`FINISHED_MATCH_FROZEN` in
`src/core/matchGuards.ts`): `id, title, teamA, teamB, rules, firstServe, summary, status, createdBy, scorerId,
participantIds, location, scheduledAt, startedAt, finishedAt, tournamentId, fixtureId, challengeId, stream,
interestedIds, teamSizeMode, lineups, captains, startedServerAt, finishedServerAt, createdAt` (and any unknown key).
A status move after the end – back to live/scheduled, or **abandoned** (V142-7) – is `match_finished`; only an
admin can void a result (review → void). "I want to play" is offered on scheduled matches only, so it is frozen
on a finished match too (an abandoned match still takes it).

## 1.4.4 – Firebase: the result comes from the events, not the stored summary (QA V143-1..5)

Tester's 1.4.3 probes showed the per-rally summary arithmetic could still be steered (set-ending rallies written
as plain +1, re-opened sets, a forged 52:50 final while the events say B won 25:0 25:0) and it cost most of the
rules budget. 1.4.4 drops it.

**What Firebase rules enforce (trusted):**
- the event log changes by **one step** per scorer write – append one well-formed rally (side A/B, a time, an
  optional credit to a player of the side that won it) or remove the last one; at most **3,000** events
  (`MAX_EVENTS`, all backends);
- the **replay inputs are frozen once the first rally exists**: `rules`, `firstServe`, `teamA` / `teamB`,
  `participantIds`, `captains`, `teamSizeMode`; set **lineups are add-only** (a stored set's lineup can't change or
  be removed; a new set's lineup can be added – the app sets it at the start of each set);
- **abandon** by the scorer only while the log is shorter than the shortest possible win
  (`minWinEvents = (bestOf + 1) / 2 × pointsPerSet`, e.g. 50 for best of 3 to 25); a longer unfinished match can
  only be abandoned by an **admin** (status / finishedAt / updatedAt only) after checking the replay;
- **finishing** (live → finished) only with at least `minWinEvents` events (and at most one rally appended in the
  same write); a finished match is **frozen** (1.4.3 rules: credits on the last 3 rallies, POTM, admin/captain
  fields only);
- the stored `summary` only has to be **well-formed** (numbers in range, A/B/null, at most 5 set scores) – it is a
  display hint for old clients.

**What the app derives (never trusted from the document):** score, sets, set scores, winner, serving side – every
result the app shows or counts (result page, captain confirm, POTM, wallet, leaderboard, "finished" badge) comes
from the replay of the events under the frozen rules (`src/core/replay.ts`, applied in
`firebaseBackend.matchFrom`). A stored summary that disagrees with the replay sets `resultCheck: 'summary_mismatch'`;
a `finished` status whose events have no winner sets `'finished_without_winner'`. Both are flagged for admin review
(`result_mismatch` flag, badge "flagged") and **never count**. Tests: rules-tests "1.4.4: V143-1..5" (Tester's S, W
and L probes – W shows B as the winner), `src/core/__tests__/replay144.test.ts`.

**Limits (by design):** (a) a modified client can still mark a match finished early (after `minWinEvents` events)
or write a wrong summary – the app shows the replayed result and flags it; (b) by-number sides: the rules check
that the **first 3** players of each side have a profile (1.4.3 checked 4) – the budget for the 12-a-side create;
the app and API check every player; (c) the scorer can no longer abandon a match that may already have a winner –
an admin does it; (d) lineups are add-only, not fully frozen (set 2+ lineups are set during the match).

**Rules budget (1.4.4, measured with padding; 1 pad ≈ 5 expressions of the 1,000 limit):** creates – 6-a-side live
28 pads spare, 12-a-side live with title and place 18, team 12 live 20, scheduled 18–29; updates at 3,000 events
with 28-character uids – finish 88, rally 110, undo 133, re-credit (live) 65, re-credit (finished) 128, POTM 168,
confirm 141, lineup add 137, roster change before the first rally 43, going live 92, abandon 86. The create path no
longer evaluates the update checks (separate `createAllowed` / `matchCreateOk`). rules-tests "V143-5 budget" re-runs
the worst cases with 10 pads on create and 30 on update.

## 1.4.5 – abandon policy: INTERIM, PENDING DECISION (QA V144-1/2/3)

- **Not decided.** Akshit hasn't chosen how an abandon after the first rally should work. 1.4.5 ships the neutral
  interim **'review'** policy: the match is abandoned and waits for an admin's review; the record keeps who abandoned
  it, when (server time), the event count, the replayed score then and a "side behind" marker (**information only**,
  never a penalty). The admin reinstates the match (live again, or finished if the log already has a winner) or
  confirms the abandon. 'flag' (behind shown as the reason) and 'consent' (the opposing captain must agree, or an
  admin decides; scoring frozen meanwhile) are implemented and tested. Switch: `src/core/abandonPolicy.ts` +
  `node scripts/gen-abandon-policy.js` (docs/qa/RELEASE-1.4.5.md).
- **Opposing captain's Report:** a captain of the side opposing whoever abandoned it can send an abandoned match back
  to admin review once (not after an admin decided, not after a 'consent' abandon they agreed to).
- **Latches on every backend:** `maxEvents` (the most events the log ever had – undo never lowers it) and `wasWon`
  (set by the finishing write). The scorer can't abandon once `maxEvents` reached the shortest possible win or the
  match was ever won; rules / first serve can't change once a rally ever existed. Only an admin's re-open of a match
  finished *without* a winner clears `wasWon`.
- **Finished without a winner (V144-2):** listed for admins; reopen as live / mark abandoned / void.
- **Admins never act on their own match (V144-3):** creator, scorer, participant or captain.
- **Firebase:** the rules check the record's shape, author, server time and event count; the score and "behind" in
  it are written by the app (the rules can't replay) – the admin sees the replayed score on the match page anyway.

## 1.4.5 – scorer handoff: INTERIM (QA V144-8)

- After the first rally scoring can only be handed to a participant on the current scorer's side (a neutral scorer:
  another neutral participant) or to an admin (API / demo). An admin who isn't part of the match can reassign it to
  any participant; that is recorded (`scorerReassign {from, to, by, at}`, `from` = the scorer before the first
  reassignment).
- A handoff never resets `maxEvents`, `wasWon`, the abandon state or the verdict: the captain who confirms the result
  is always the one opposing the scorer at match start (`scorerReassign.from`).
- **Firebase:** the rules can't read another user's admin claim, so a scorer can't hand to an admin there; the admin
  reassigns instead (their own claim is checked).
- Marked interim: the product rule for handoffs hasn't been decided either.

## 1.4.5 – rankings / wallet reads on Firebase (QA V144-5)

- A client-written aggregate was rejected (the rules can't tie it to the events). **Plan:** a trusted writer (Cloud

## 1.4.6 – one lifecycle (QA V145)

- **Client-only checks (`LC_CLIENT_ONLY`):** the Firebase rules can't replay a match, so two checks are made only by
  the clients (and the API): an admin abandon of a *live* match whose events already have a winner (rules: allowed
  unless `wasWon`), and voiding a won finished match before its POTM (rules: allowed). Both are admin-only actions.
- **No-op writes:** writing the status a match already has (e.g. `scheduled` on a scheduled match) and the same captain
  replaying the same verdict (API, AF-45) are accepted as no-ops; the walks skip / check them as no-ops (`walkSkip`).
- **Delete:** a match that ever had a rally is never deleted, by anyone (admins void instead). The demo app has no delete.
- **Rankings / wallet on Firebase (V145-8):** a hard byte budget of 24 MiB per read, shared by priority tiers (own
  matches 25 % of what is left, approved 30 %, confirmed 60 %, finished the rest; at most 200 / 200 / 300 / 500
  documents). A page asks for at most ⌊bytes left / 512 KiB⌋ documents, so with documents within the size the rules
  allow (≤ 3,000 events, < 512 KiB) the read never exceeds 24 MiB. **Worst case:** a legacy document near Firestore's
  1 MiB limit could make one page read up to twice what was left – at most ~48 MiB in total. Beyond the caps the oldest
  matches aren't counted on Firebase (the plan for a trusted aggregate writer from 1.4.5 still stands).
- **Handoff to an admin (V145-17):** API / demo list the admins who may take over (`GET /matches/:id/handoff-admins`,
  creator / scorer only, id + name). Firebase can't (the rules can't see another user's admin claim): the app offers
  "Ask an admin to take over", which opens a message to the support address (or the share sheet when none is set) –
  nothing is sent automatically, and an admin then reassigns the scorer. An in-app takeover request would need a new
  rules field; not done.
- **Abandon policy:** still interim ('review'), pending Akshit's decision.
